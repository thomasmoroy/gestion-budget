# Supabase (auth + PostgreSQL)

Référence pour ce projet : React + Express + Supabase (Postgres hébergé + Auth Google), isolation des données par utilisateur.

## Architecture

- **Client** (`client/src/supabase.ts`) : `createClient(VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY)` ; flag `supabaseConfigured` → écran « Configuration requise » si manquant.
- **Serveur** (`server/src/auth.js`) : vérifie le jeton `Authorization: Bearer <access_token>` avec `supabase.auth.getUser(token)` (cache 60 s), expose `req.userId`.
- **API** : toutes les routes sont montées derrière `requireAuth` et filtrent explicitement `WHERE user_id = $n`.
- **BDD** : `server/src/db.js` (pool `pg`, helpers `q`/`q1`/`run`), migration `server/migrations/001_init.sql` appliquée au démarrage (`migrate()`).

## Auth Google

```ts
// client : connexion
await supabase.auth.signInWithOAuth({
  provider: 'google',
  options: { redirectTo: window.location.origin },
})
// session : supabase.auth.getSession() / onAuthStateChange dans src/auth.tsx
```

- Client ID/Secret Google → **Supabase Dashboard → Authentication → Providers → Google** (jamais dans le code).
- Redirect URI côté Google Cloud : `https://<ref>.supabase.co/auth/v1/callback`
- URL de retour : **Authentication → URL Configuration** (`http://localhost:5173` en dev).
- 401 côté client → `signOut()` automatique (`client/src/api.ts`).

## RLS et isolation

Principe retenu dans `001_init.sql` :

- Chaque table porte `user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE`.
- `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` **sans policy** → les rôles API (`anon`, `authenticated`, `service_role`) sont en déni par défaut (le REVOKE DO-block double la protection).
- Le serveur se connecte en `postgres` (propriétaire des tables → bypass RLS) et fait lui-même le filtrage par `user_id` issu du JWT vérifié.

Ne jamais ajouter de policy permissive pour `anon`/`authenticated` : cela exposerait les données via PostgREST. L'isolation se fait dans les requêtes Express.

## Migrations SQL

- Idempotentes (`IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`) : elles tournent à chaque démarrage.
- Dialecte Postgres : `BIGINT GENERATED BY DEFAULT AS IDENTITY` (pas d'AUTOINCREMENT), `TIMESTAMPTZ`, `BOOLEAN`, `RETURNING id` (pas de `lastInsertRowid`).
- `ON CONFLICT (...) DO UPDATE SET x = EXCLUDED.x` pour l'upsert (budgets).
- Erreur de contrainte d'unicité : `e.code === '23505'`.
- La contrainte FK sur `auth.users` impose que le schéma existe : sur un Postgres local, créer d'abord `CREATE SCHEMA auth; CREATE TABLE auth.users (id UUID PRIMARY KEY);`.

## Côté pg (driver Node)

- Les parsers de types sont posés dans `db.js` : `int8 (20)` et `numeric (1700)` → `Number` (montants en centimes), `date (1082)` → chaîne `YYYY-MM-DD`.
- `sslmode=require` dans `DATABASE_URL` → `ssl: { rejectUnauthorized: false }`.
- Montants stockés en **centimes** (entier), jamais en float.

## Variables d'environnement

| Fichier | Variable | Origine |
|---|---|---|
| `client/.env` | `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` | Dashboard → Settings → API |
| `server/.env` | `SUPABASE_URL`, `SUPABASE_ANON_KEY` | idem |

`TEST_USER_ID` : borne de test locale uniquement (jamais en production, jamais dans `.env.example`) ; active aussi l'en-tête `x-test-user`.

## Tests

`npm test` → `server/test/smoke.mjs` : poste **PGlite** (Postgres WASM) comme `__TEST_POOL__`, applique la vraie migration, démarre l'app et exerce l'API avec deux UUID utilisateurs pour vérifier l'isolation. Aucun réseau ni projet Supabase requis.
